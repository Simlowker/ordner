# Technical report — Ordner

**Ordner reads Swiss bank tax statements on a laptop, grades itself against each statement's own barcode, and tells the user which values to check.**

## 1. Summary

Young adults in Switzerland face their first tax return untaught, and the documents involved contain sensitive personal data. Ordner reads the summary page of a bank tax statement (eCH-0196) from a photo or scan, extracts the eight values a taxpayer needs, flags those it may have misread, explains with verified quotes from official guides where each value goes, and runs on one laptop. Apertus 1.5 8B is the core: fine-tuned with LoRA, it writes the fields as JSON and the explanations, and a linear probe on its hidden states estimates whether each field is wrong. LightOnOCR-3 (OCR), d1-3B (single-pass judge), EmbeddingGemma 2 (retrieval) and deterministic checks support it. Labels cost nothing: every eCH-0196 statement stores its full XML in Macro-PDF417 barcodes, which we decode as ground truth. On 1,200 frozen test pages (120 synthetic statements, three layouts of which two are never seen in training, up to four degradation levels), field-level exact match is {{acc_regex_test}} for OCR + rules, {{acc_base_test}} for zero-shot Apertus and {{acc_lora_test}} after fine-tuning ({{acc_lora_unseen}} on the unseen layouts; H1: {{h1_verdict}}). Re-reading the most doubtful {{triage90_combined}} of fields catches 90 % of zero-shot errors (combined AUROC {{auroc_combined}}, H2: {{h2_verdict}}; probe alone {{auroc_probeA}}, H3: {{h3_verdict}}). No external service is called at runtime.

### Problem and motivation

- **Not taught.** In 2023, 9.5 % of 18-24-year-olds lived in a household with at least one tax arrear (FSO figure cited in a St. Gallen parliamentary interpellation of 3.3.2026 [20]; we have not checked the original FSO table). In 2022, 40.9 % of the population lived in an indebted household and 5.5 % in one with tax arrears (FSO SILC 2022, reported by SRF [21]). In a representative survey (n = 1,506), 77 % said they taught themselves about money [22], and Switzerland does not take part in PISA's financial-literacy assessment [23].
- **Why local.** A tax file contains sensitive data under art. 5 lit. c nLPD/FADP (religion via church tax, health, social assistance) [17]; a cloud service makes the provider a processor (art. 9) and often implies disclosure abroad (art. 16-17). Every AI tax assistant we found is cloud-based: PostFinance TaxOptimizer, PaperTax (LLM processing in the United States, according to its website), and the Budgetberatung chatbot (OpenAI; it asks users not to enter bank or health data) [24]. None publishes an evaluation.
- **Why read the page when a barcode exists.** VaudTax cannot import a scanned statement because scanning damages the barcodes [25], and pillar 3a certificates, health-insurance letters and many foreign brokers' statements have no machine-readable part. The useful skill is reading the human-readable page; a clean barcode only serves to measure it.

### Contributions

1. **The document grades itself.** To our knowledge, no prior work uses a payload printed on the same document (here the eCH-0196 barcode) as ground truth for both evaluating and fine-tuning extraction from the human-readable part [18]. Labels are exact, unlimited, and need neither annotators nor a closed model.
2. **Doubt read inside an open model, combined with an external judge.** A probe on Apertus hidden states, a calibrated single-pass judge (d1-3B) and deterministic checks are fused into one field-level doubt score for human triage, with pre-registered hypotheses. Phillips et al. [1] fuse a probe with entropy, Jin et al. [3] decompose document confidence into channels; to our knowledge this combination has not been evaluated for document field extraction, nor on Apertus.
3. **Re-runnable locally.** `make run` replays the full evaluation in Docker without GPU, weights or network; we report cost per page on a named laptop.

**Related work.** Selective prediction is evaluated by risk-coverage [13]. Hidden-state probes detect hallucinated entities better than token uncertainty (AUC 0.85 vs ≤ 0.76 on Llama-3.1-8B [6]) at almost no cost [7]. Small calibrated judges can guarantee agreement levels [2]; HALO [4] bounds generative errors with deterministic checks; OCR-then-LLM cascades remain strong baselines [14]. Among public Hack Apertus Track 2B repositories (searched 14.10.2026; private ones are not visible) we found none on tax statements and none reading hidden states.

## 2. Architecture

```
page image (photo / scan)                                    Figure 1. Pipeline (stages run as resumable batches)
  └─► LightOnOCR-3-1B ......... OCR → Markdown text                                   [support]
        └─► Apertus 1.5 8B + LoRA .. 8 fields as JSON (greedy, thinking off)          [core]
              ├─ token log-probs and entropies of each value
              ├─ hidden states (one teacher-forced pass) ─► linear probe: P(field wrong)
              ├─ d1-3B ............. "Is <value> the <field> shown in this document?" → P(yes)   [support]
              └─ deterministic checks (35 % rule, A + B totals, value present in the OCR text, ...)
                    └─► combined doubt (logistic regression) ─► triage: only doubtful fields go to a person
                          └─► EmbeddingGemma 2 retrieval [support] ─► Apertus explanation, quotes checked verbatim
                                └─► console: fields coloured by doubt, triage slider, explanation, deduction checklist
```

**Deterministic checks** (layout label never used): non-negative amounts; withholding claim = 35 % of revenue A within display rounding; each value present in the OCR text (twice when a totals row is printed); A + B and footnote totals consistent; valid canton code; tax year = period end.

**Data flow.** Stages run one model at a time on two Apple M4 Max machines (36 GB) and write resumable JSONL files. Apertus (extraction with hidden states, LoRA training, explanations) ran on the second machine, OCR and d1-3B on both depending on the phase. Apertus alone produces the extracted values; the other components only score them.

**Explanation.** The corpus holds 151 passages (80-200 words, none written by hand) from nine official documents (`data/corpus/SOURCES.md`): ESTV circular 2-215 (de/fr/it), Bern guide (de/fr), Ticino and Graubünden guides (it), eCH-0196 (de/fr). EmbeddingGemma 2 retrieves up to six passages in the user's language; Apertus (base weights, greedy, thinking off) writes at most 170 words, quoting them as «…» [passage id]. Code checks every quote word for word against its passage (after Unicode, whitespace and apostrophe normalisation), fixes the id if the quote sits in another retrieved passage, removes it otherwise, and appends a fixed warning for every red field (combined doubt ≥ 0.5). A checklist applies 20 deterministic deduction rules (federal direct tax and pillar 3a, 2026, ESTV circular 2-215-D-2025 [19]), each with its source and verification status. The wording informs; it never advises.

### Target architecture (mandatory)

Ordner is deployable as **b) air-gapped** (primary) and **a) on-premise**.

- **Runtime external services: none.** Local weights, no API key; the console serves only local files (CSP `default-src 'self'`, no CDN, no telemetry). The video shows a run with Wi-Fi off.
- **Build time only (online, once):** model weights from Hugging Face, Python packages, the Docker base image (pinned by digest), the official PDFs of the explanation corpus, and, for data generation, OpenSteuerAuszug and its PDF417 encoder fork from GitHub.
- **b) Air-gapped:** once built, a 36 GB Apple Silicon Mac runs everything offline; the `make run` image holds no model and no remote client.
- **a) On-premise:** e.g. a workstation of a budget or debt counselling service, under its own administration; no document leaves the premises (transformers wrappers also exist for non-Apple hardware).
- **c) Sovereign Swiss cloud** is not targeted: keeping tax data on the user's machine is the point.

## 3. Use of Apertus

- **Model:** `swiss-ai/Apertus-v1.5-8B`, text backbone exported as `andreasmartin/apertus-v1.5-8b-text` (Apache-2.0), revision `c0e7eeb`
- **How it is used:** inference (extraction, explanation), fine-tuning (LoRA), evaluation (white-box doubt probe)
- **Where it runs:** local weights; MLX / mlx-lm, bf16 without quantisation, on an Apple M4 Max (36 GB)

**Prompt and decoding.** A one-line system message asks for one JSON object; the user message lists the eight fields with trilingual label hints, output rules (fixed keys, plain decimals, `null` if absent) and the OCR text (`src/ordner/models/apertus.py`). Thinking is disabled; decoding is greedy (≤ 256 new tokens), log-softmax in float32. Missing or unparseable values count as wrong.

**Numerical check.** We use MLX because transformers swapped heavily on 36 GB. On a validation page, MLX and transformers (bf16, CPU) gave an identical greedy answer and hidden states with cosine ≥ 0.9996 at the probed positions; transformers on MPS deviated on some prompt tokens in our smoke test (cosine down to 0.74), hence the CPU reference.

**Hidden states.** After generation, one teacher-forced pass over prompt and answer reads the residual stream after decoder layers 4, 8, …, 32. Per field we keep position A (mean over the value's tokens) and position B (the token just before the value). Apertus's residual norm grows about a thousandfold with depth (mean answer-token norm ≈ 6 after the embeddings, ≈ 6,000 at layer 31), and the BOS token reaches |x| ≈ 1.2 × 10⁵ from layer 3 on, consistent with the exploding activations reported by Claritas on Apertus v1 [8]. We therefore keep float32 wherever float16 would overflow, standardise each dimension before a 256-component PCA fitted on training items only, and choose the layer and regularisation of the logistic-regression probe by cross-validation grouped by statement on train + dev.

**LoRA fine-tuning.** mlx-lm LoRA: rank 16, scale 2 (α = 32), dropout 0, all 32 blocks; Adam, learning rate 10⁻⁴, batch 2, 420 iterations (2 epochs over 420 training pages), 2,048 tokens max, gradient checkpointing, loss on the answer only, seed 7. Inputs are degraded training pages in the exact extraction prompt; targets are the oracle values as displayed, in the zero-shot JSON layout; we assert that each training sequence tokenises to exactly the extraction prompt plus target (mlx-lm would otherwise enable thinking in the template). Validation loss on dev fell from 0.343 to 0.003 (best, 0.003, at iteration 300); we use the final adapter (iteration 420), fused into the weights, without checkpoint selection. Training took about 2 h (peak {{lora_peak_gb}} GB).

## 4. Data

**Generator.** Fictional statements (seed 7): fictional bank and client, 1-4 accounts (CHF, EUR, USD), 0-6 securities (Swiss dividends with 35 % withholding tax), a loan in 25 % of cases, language set by canton. Totals are cross-checked by an independent recomputation and OpenSteuerAuszug's verifier (MIT [16]); the XML follows eCH-0196 v2.2 [15]. 600 statements: German 255, French 199, Italian 146 (2 redrawn because the barcode encoder rejected their payload size).

**Layouts and degradations.** _Layout A_ is OpenSteuerAuszug's renderer: a 5-8 page PDF whose last pages carry the Macro-PDF417 barcodes; models only see page 1 (the summary), rendered at 200 dpi greyscale. _Layout B_ (ours, reportlab, test only) is a compact one-page summary table with different typography, labels and number format. _Layout C_ (ours, test only) is a portrait bank letter: the total tax value sits in a side panel ("Auf einen Blick" / "En bref" / "In breve"), revenues and the withholding claim in a bottom box ("Données pour votre déclaration d'impôt" and its German and Italian equivalents), position tables add distractor subtotals, and amounts read "CHF 12 345.60" with a no-break space (68 documents) or carry no separator (52). _Degradation_ levels 1-3 simulate phone photos (perspective, rotation, shading, contrast, blur, noise, JPEG quality 85 down to 25), seeded per page; level 0 is the clean render.

**Oracle.** zxing-cpp reads the barcode segments of the clean layout-A PDF; segments are ordered, concatenated, zlib-decompressed and parsed. The decoded fields match the generator's values for all 600 statements (0 mismatches), and in all 840 documents (600 A, 120 B, 120 C) the four displayed totals occur in the PDF text layer. **Gold is the value as displayed:** layout A prints three totals rounded to whole CHF (the withholding claim with 2 decimals); layouts B and C print 2 decimals.

**Splits** (by statement, PREREG):

| Split | Statements | Pages | Composition                                                                       |
| ----- | ---------- | ----- | --------------------------------------------------------------------------------- |
| Train | 420        | 420   | layout A, one random degradation level per page                                   |
| Dev   | 60         | 60    | layout A, one random degradation level per page                                   |

**Licence and privacy.** All documents are fictional and contain no personal data; they are generated with MIT-licensed tools, and the official `taxstatement` jar is neither used nor redistributed. Generated data is released under CC0 ({{hf_dataset_url}}). `data/` (< 100 MB) holds `items.jsonl` (one row per page × field × system), `probe/{A,B}.npz` (PCA-256 projections, float16), demo pages, deduction rules and `corpus/passages_public.jsonl`: only the 56 redistributable passages (eCH-0196, free with attribution, and the federal circular). Cantonal guides carry no reuse licence and are rebuilt locally (`python -m ordner.explain.corpus --download`).

## 5. Evaluation

**Protocol (PREREG.md).** Field-level exact match on test after normalisation (amounts as Decimal with 2 decimals; strings case-folded, whitespace collapsed). 95 % CIs: paired cluster bootstrap over the 120 test statements (10,000 resamples, seed 0); models are fit once, so CIs reflect test sampling only. **H1:** fine-tuning raises accuracy (CI of the paired difference excludes 0). **H2:** the combined doubt score has a higher AUROC for "field is wrong" than every single signal. **H3:** the position-A probe has AUROC > 0.5 (CI lower bound > 0.5). **Baselines:** OCR + rules/regex without LLM, whose label patterns were written from layout-A train/dev pages (like the deterministic checks, it knows only layout A); OCR + zero-shot Apertus; for doubt, minimum token probability, mean token entropy, d1-3B validation and the deterministic checks.

**Doubt study.** Doubt is studied on zero-shot outputs (primary), because LoRA outputs on training pages are overfit and contain few errors; LoRA outputs are generated for dev and test only. Probe and combination are fit on train + dev and scored on test; the combination is a logistic regression over token statistics, d1 P(yes), check results and the out-of-fold probe score. For the fine-tuned system, a combination without the probe is calibrated on dev (secondary). Triage = share of fields a person re-reads, most doubtful first, to catch 80 / 90 / 95 % of wrong fields; a missing signal counts as maximal doubt.

## 6. Limitations

- **Synthetic documents.** All pages are generated: one real-world renderer family (OpenSteuerAuszug) and two layouts of our own (B, C). They test generalisation beyond a single layout, not to real bank statements; amounts, names and positions follow our own distributions.
- **Rounding as displayed.** Layout A prints totals rounded to whole CHF and gold is the displayed value: we measure reading, not recovery of the exact XML value.
- **The barcode makes the task moot when readable.** A decoder then suffices. We calibrate on barcode documents to deploy where the barcode is missing or damaged (scans, photos, pillar 3a and insurance documents), a distribution we have not measured.
- **Doubt study.** The probe is trained on zero-shot errors; the deployed LoRA system needs a refit on its own errors (free barcode labels allow it; not done). CIs ignore refitting variance; LoRA used one seed.
- **Pipeline choices.** Apertus reads OCR text, not the image (its native vision runs only in unmerged MLX forks). Router accuracy is not evaluated: the corpus has a single document type.
- **Licences.** d1-3B's LFM Open License 1.0 is not OSI-approved, and "revenue" is ambiguous for a public administration; an Apache-2.0 alternative (Cloudflare clef-flash) was not evaluated. The cantonal guides are not redistributed, so a clean checkout explains from eCH and ESTV passages only until the corpus is rebuilt.
- **No human study.** We have not tested whether triage and explanations help young adults or counsellors, nor judged explanation correctness beyond automatic checks.
- **Demo.** The layout-B demo page comes from the test split; it is shown for display only and nothing was tuned on it.

## 7. Reproducibility

**Replay (judges).** `make run` builds a `python:3.12-slim` image pinned by digest (numpy 2.4.6, scikit-learn 1.9.1, matplotlib 3.10.9), refits probe and combined model from `data/items.jsonl` and `data/probe/*.npz`, recomputes every test statistic, writes `data/results/` and serves the console on `http://localhost:8000`; no GPU, weights or network. `make eval` runs the replay only.

**Live pipeline (Apple Silicon, outside Docker, which cannot use the Mac GPU).** Python 3.11 in `.venv` with torch 2.14.1, transformers 5.19.0, accelerate 1.15.0, sentence-transformers 6.1.0, mlx 0.32.3, mlx-lm 0.32.0, zxing-cpp 3.1.1, pypdfium2 5.14.0, reportlab 5.0.1, scikit-learn 1.9.1, and OpenSteuerAuszug at commit `eeb3b3d` (which pulls the `vroonhof/pdf417-py` fork, commit `44ce800`). Model revisions (`docs/model_revisions.txt`): Apertus text backbone `c0e7eeb`, LightOnOCR-3-1B `23d5440`, EmbeddingGemma 2 `914f7f8`, d1-3B `051bcc4`.
